# Working inside the Herdr desktop app

Read this on the first turn inside the Herdr desktop app, as the global instructions say. Terminals run in herdr-core (`hc`), and `herdr-app` arranges the window. `$HC_TERMINAL_ID` is your terminal's address, like `t1`. The tab rename needs no skill; for any other command, load the `hc` and `herdr-app` skills, which hold the full commands. The commands here are written for Bash; in PowerShell, write `$env:HC_TERMINAL_ID`, since `"$HC_TERMINAL_ID"` there expands to nothing.

## Names

- **Name the tab first.** On the first turn, when you are the only agent and neither your first prompt nor `hq` named the tab, name your tab before you read the repo or start the task, even for a short question. Your tab is the one `herdr-app ls` lists your address under, and `herdr-app do tab.rename --id <tab> --name <slug>` names it. With no pane there, as an `hq` worker has, skip the rename: without a tab of your own it would rename the one I'm looking at. I don't name tabs myself, so whatever label is there, a number, the harness's name like `Claude Code`, or a previous agent's slug, is yours to replace. When the first message is too thin to name, rename on the turn the task becomes clear, and rename again when the task changes enough that the label would mislead.
- Rename what you own whenever a name clearly helps: your tab and the agents you start. Don't label yourself unless a skill like `hq` says to: the agents panel shows your harness's own session title, with your tab name beside it. A `tc.agent` label is for a name another session gives, like the next session you start below or one `hq` picks up. A name another session gave you stays, and so does everything another session owns. Name an agent you start for its role or task, like `reviewer` or `nav-flicker`.
- **Each name says only what the level above it doesn't.** Names are lowercase slugs of one to three words, at most 16 characters, which is my sidebar width. A worktree's space already carries the task, so a tab there is named for its role, like `build` or `review`, not the task again. Start each server with its port in the command, like `pnpm dev --port 3001`, so other sessions can see which ports are taken in the `argv` of `hc get <t> --json`, and keep a worktree's branch short, since the space shows it.
- I prefer three panes per tab. The next one goes in a new tab named for what it holds.
- **Never take my focus or my input.** Open a new tab with `hc run --bg --no-notify --label herdr.space=<space id>` rather than `tab.new` or `space.new`, which bring it to the front; I open it from the agents list. `--no-notify` stops `hc` typing notes into your terminal, which is where I type; watch what you started instead with one background `hc wait --children any`, whose news arrives as a task notice. In general, reach another session through an API, like cross-session messages, OpenCode's server, or `hc wait`, before keystrokes. Type into an agent's input with `hc keys` or `hc send` only for a prompt nothing else can answer, like a Claude Code plan or permission card, or to relay my own approval, which a Claude Code session won't take from another session's message.

## Panes, servers, and sessions

- **A pane is for what outlives the session or needs me.** A dev server, a watcher, something I asked to watch, or a command that waits for my input runs in a sibling pane, never as a background job of the harness. Tests, builds, checks, and other commands that finish on their own run through the harness's own tools as usual; this wins over the `hc` skill's advice to run slow work like builds and tests in an `hc` terminal. Before starting a server, check `hc ls` for one already running in this checkout and reuse it.
- `pane.split` splits whichever pane I have focused, so always pass `--pane <your pane>`, which `herdr-app ls` lists beside your address. A server goes in `herdr-app do pane.split --direction right --pane <your pane> --argv '["pnpm","dev","--port","3001"]'`, and `hc wait <t> --output <text> --timeout <s>`, started right after the split, waits for its ready line. When a request fails, read the server's output with `hc read <t>`.
- **With no pane.** An `hq` worker is a child shown only in the agents list, so it starts terminals with `hc run --bg` instead of a split: a server as its own child with `--no-notify`, with `--outlive-parent` when it should stay up after you, and the next session as described below. I open either one by clicking it in the agents list.
- When the global fresh-session split says to stop, start the next session yourself, on this same harness and the model this session runs on. It goes in a split the same way: `claude` with `--name`, `--model`, and the `--effort` and `--autocompact` your task named, and its whole first prompt, which hands it the plan file path and the slice to build, as the last item. In OpenCode, which takes no model flag, create the session first with `opencode api session.create` on your model and variant, then start `opencode -s <session id> --prompt "<first prompt>"`. Then label it `tc.agent=<name>`. With no pane, start it with `hc run --bg --name <its name> --parent <your parent> --outlive-parent --no-notify`, taking the parent from `hc get "$HC_TERMINAL_ID" --json`, so it nests where you did. Name it after your own agent name with the next free number, like `nav-flicker-2` from `nav-flicker` and `nav-flicker-3` from `nav-flicker-2`, or after the task's slug when you have no name, and give that name, plus its session id when it runs in OpenCode so `hq` can reach it through the server, in this session's report, which you then finish.
- A helper whose result comes back into this task, like a review, research, or a lookup, runs as a subagent, since a pane is a whole second session to start and clean up. Start a helper in a pane the same way only when it has to outlive this session, when I asked to watch it, or when it needs a harness or model your subagents can't run, and `hc wait <t> --timeout <s>` watches for it to block or finish.
- **Notifications.** There's no command for one. The app alerts on its own when an agent blocks or finishes, so ending your turn is the notification. A notice the global rules send while you keep working, like an environment failure, goes in an update line instead, and the close repeats it.
- **Worktrees.** Run `git -C <this checkout> fetch origin`, then `git -C <this checkout> worktree add --no-track ~/.herdr/worktrees/<repo>/<slug> -b <branch> origin/<default branch>`, where the slug is the branch with each slash turned into a dash. That starts from the default branch and leaves the upstream for the first push to set. To give it a space without taking my focus, which `space.new` does, run `hc run --bg --outlive-parent --no-notify --cwd <that path> --label herdr.space=sp-<slug>-<unix time> --label herdr.tab=tb-<slug>-<unix time>`. Its servers and its next session go in that space.
- **Closing.** `hc kill <t>` ends a terminal you started, and `hc rm <t>` then removes it, so finished terminals don't pile up. Never stop or restart the core, which runs every terminal I have.
